# Codex Collaboration Workflow

이 문서는 GOPS 프로젝트에서 Codex 채팅방을 장기적으로 운영하기 위한 협업 규칙이다.

GOPS는 팀원별 스펙과 우리 담당 차트/프론트엔드 구현이 함께 움직이는 프로젝트이므로, 대화, 검토, 구현 역할을 분리해 결정 품질과 구현 안정성을 높인다.

현재 운영 방식은 같은 local 프로젝트 폴더를 공유하는 멀티 채팅 구조다. 별도 worktree는 사용하지 않는다. 따라서 구현 작업은 한 번에 하나의 채팅방이 맡고, Navigator는 사용자의 대화 흐름을 유지하는 것을 우선한다.

## 채팅방 구조

| 역할 | 이름 | 책임 |
| --- | --- | --- |
| 메인 대화 채팅방 | `GOPS Navigator` | 사용자와 구현 방향, 설계 판단, 작업 범위, 우선순위, 최종 결정을 이어가는 중심 채팅방 |
| 방향성 검토 채팅방 | `GOPS Compass` | 프로젝트 문서, 팀원 스펙, 제품 방향, 아키텍처, 책임 경계 기준으로 계획과 설계를 검토하는 채팅방 |
| 구현 전담 채팅방 | `GOPS Forge` | Navigator에서 충분히 정리된 구현 요청을 받아 구현, 테스트, 검증, 결과 보고를 수행하는 채팅방 |

최종 판단은 항상 사용자와 `GOPS Navigator`가 함께 한다.

현재 메인 대화 채팅방 식별 정보:

- `GOPS Navigator`: `019effe8-d2d8-79c3-9e6c-98a5beedeafb`

Compass 또는 Forge가 Navigator에 직접 보고할 수 있는 thread management 도구를 가진 경우 위 식별 정보를 사용한다. 도구가 없거나 전송에 실패한 경우에는 현재 채팅방에 `Navigator 전달용 보고서`를 남겨 사용자가 Navigator에서 회수할 수 있게 한다.

## GOPS Navigator

`GOPS Navigator`는 사용자가 주로 대화하는 메인 협업 허브다.

책임:

- 사용자와 구현 방향, 설계 판단, 작업 범위, 우선순위를 논의한다.
- 필요하면 직접 문서와 코드를 읽는다.
- `GOPS Compass`에 방향성 검토를 요청한다.
- `GOPS Forge`에 구현을 요청한다.
- 검토와 구현 결과 보고를 받아 해석, 진단한 뒤 사용자와 다음 결정을 이어간다.
- 중요한 결정과 변경 사항을 프로젝트 문서에 남긴다.

하지 말아야 할 일:

- 구현 방향이 확정되지 않은 상태에서 구현 전담 채팅방에 작업을 넘기지 않는다.
- 단순 아이디어나 미정 상태의 논의를 확정된 요구사항처럼 취급하지 않는다.
- `GOPS Compass` 또는 `GOPS Forge`의 결과를 사용자 판단 없이 최종 결정으로 고정하지 않는다.
- Compass 또는 Forge의 진행 상황을 계속 polling하지 않는다.
- 다른 채팅방이 구현 중인 파일을 동시에 수정하지 않는다.

## GOPS Compass

`GOPS Compass`는 방향성 검토 전담 채팅방이다.

책임:

- `docs/README.md`, `docs/spec/README.md`, 관련 스펙 문서를 기준으로 검토한다.
- 메인 채팅방에서 정리한 계획이나 설계가 전체 프로젝트 방향과 충돌하지 않는지 확인한다.
- 누락된 전제, 위험한 가정, 문서 간 불일치, 책임 경계, 장기 유지보수 관점을 중심으로 피드백한다.
- 필요하면 임시 서브에이전트를 사용해 검토를 병렬화한다.

하지 말아야 할 일:

- 직접 구현하거나 파일을 수정하지 않는다.
- 세부 구현 방식만 보고 제품 방향과 책임 경계를 놓치지 않는다.
- 최종 결정을 대신 내리지 않는다.

## GOPS Forge

`GOPS Forge`는 구현 전담 채팅방이다.

책임:

- `GOPS Navigator`에서 충분히 정리된 구현 요청을 받아 실제 구현에 집중한다.
- 구현, 테스트, 검증, 결과 보고까지 수행한다.
- 필요하면 임시 서브에이전트를 사용해 탐색, 구현, 테스트, UI 검증을 병렬화한다.
- 구현 요청이 불명확하면 바로 구현하지 않고 필요한 질문이나 전제 확인을 `GOPS Navigator`에 요청한다.

하지 말아야 할 일:

- Navigator에서 구현 방향이 확정되기 전에 파일을 수정하지 않는다.
- 구현 범위, 완료 기준, 수정 대상, 검증 방법이 불명확한 상태에서 작업을 시작하지 않는다.
- 같은 local 프로젝트 폴더에서 운영되므로, Navigator 승인 없이 독자적으로 문서나 코드를 변경하지 않는다.
- 같은 local 프로젝트 폴더에서 운영되므로, 다른 채팅방과 동시에 쓰기 작업을 하지 않는다.
- 최종 제품 판단을 대신 내리지 않는다.

## 공유 폴더 운영 원칙

`GOPS Navigator`, `GOPS Compass`, `GOPS Forge`는 같은 local 프로젝트 폴더를 기준으로 협업한다. 별도 worktree를 만들지 않는다.

운영 원칙:

- Navigator는 메인 대화 흐름을 유지하고, Compass/Forge의 중간 진행을 지속적으로 감시하지 않는다.
- Compass는 기본적으로 읽기 전용 검토만 수행한다.
- Forge는 Navigator에서 정리한 구현 요청 하나만 수행한다.
- Forge가 구현 중이면 Navigator와 Compass는 같은 파일을 동시에 수정하지 않는다.
- Forge 또는 Compass의 결과는 완료 보고나 사용자의 수동 보고 트리거를 통해 회수한다.
- Navigator는 보고서를 그대로 실행하지 않고, 해석과 진단을 거쳐 사용자와 다음 방향을 정한다.

## 트리거 규칙

`4869`와 `8520`은 `GOPS Navigator`에서만 해석한다. `7410`은 `GOPS Compass`와 `GOPS Forge`에서만 해석하는 보고 트리거다.

### `4869`

방향성 검토 요청 트리거다.

해석 조건:

- 메시지가 `4869` 단독으로 쓰였을 때
- 메시지 맨 앞에 `4869`가 명령처럼 쓰였을 때

동작:

- Navigator가 현재까지의 논의, 관련 문서, 검토받고 싶은 쟁점, 아직 확정되지 않은 부분을 정리한다.
- 정리된 요청을 `GOPS Compass`에 전달한다.
- 정보가 부족하면 바로 전달하지 않고 사용자에게 최소한의 질문을 한다.
- Navigator는 Compass 진행 상황을 계속 polling하지 않는다.
- Compass 검토 결과는 Compass의 최종 보고 또는 `7410` 보고 트리거를 통해 회수한다.
- Navigator는 회수한 결과를 해석하고 사용자와 다음 판단을 이어간다.

### `8520`

구현 요청 트리거다.

해석 조건:

- 메시지가 `8520` 단독으로 쓰였을 때
- 메시지 맨 앞에 `8520`이 명령처럼 쓰였을 때

동작:

- Navigator가 구현 범위, 완료 기준, 수정 대상, 검증 방법이 충분히 정리됐는지 확인한다.
- 정보가 충분하면 정리된 구현 요청을 `GOPS Forge`에 전달한다.
- 정보가 부족하면 먼저 Navigator에서 사용자와 범위를 정리한다.
- Navigator는 Forge 진행 상황을 계속 polling하지 않는다.
- Forge 구현 결과는 Forge의 최종 보고 또는 `7410` 보고 트리거를 통해 회수한다.
- Navigator는 회수한 결과를 해석하고 변경 사항, 검증 결과, 남은 이슈를 사용자에게 보고한다.

### `7410`

작업 보고 트리거다. `GOPS Compass` 또는 `GOPS Forge`에서만 해석한다.

해석 조건:

- 메시지가 `7410` 단독으로 쓰였을 때
- 메시지 맨 앞에 `7410`이 명령처럼 쓰였을 때

동작:

- Compass 또는 Forge가 최근 작업 내역을 자세히 정리한다.
- 가능하면 `GOPS Navigator` thread id `019effe8-d2d8-79c3-9e6c-98a5beedeafb`로 직접 보고서를 전달한다.
- 직접 전달할 수 없거나 전송 여부를 확인할 수 없으면 현재 채팅방에 `Navigator 전달용 보고서`라는 제목으로 보고서를 남긴다.
- 직접 전달하지 못한 경우 보고서 첫 부분에 `자동 전달 실패 또는 불가`를 명시한다.
- 어떤 경우에도 조용히 종료하지 않는다. 직접 전송 성공 보고 또는 현재 채팅방의 전달용 보고서 중 하나를 반드시 남긴다.
- 보고서는 완료된 작업, 미완료 작업, 검증 결과, 리스크, Navigator에서 결정할 사항을 포함한다.
- `7410`은 새 검토나 새 구현을 시작하는 명령이 아니다.
- `7410`은 추가 파일 수정 명령이 아니다. 보고서 작성에 필요한 최소한의 읽기만 수행한다.

주의:

- 일반 문장 중간의 `4869`, `8520`, `7410` 숫자는 트리거로 해석하지 않는다.
- 트리거 실행에 필요한 정보가 부족하면 실행보다 질문을 우선한다.

## 검토 요청 흐름

1. 사용자가 Navigator에 `4869`를 보낸다.
2. Navigator가 검토 대상과 질문을 정리한다.
3. Navigator가 Compass에 검토 요청을 보낸다.
4. Compass는 구현하지 않고 방향성, 책임 경계, 문서 충돌, 위험한 가정을 검토한다.
5. Compass는 최종 보고를 남기고 대기한다.
6. 사용자가 Compass에 `7410`을 보내면 Compass는 최근 검토 내역을 Navigator에 직접 전달하거나, 실패 시 현재 채팅방에 Navigator 전달용 보고서로 정리한다.
7. Navigator는 Compass 보고서를 확인한 뒤 사용자에게 요약, 진단하고 최종 판단을 이어간다.

검토 요청에는 다음 항목을 포함한다.

- 현재까지의 논의 요약
- 관련 문서 경로
- 검토받고 싶은 쟁점
- 아직 확정되지 않은 부분
- 사용자가 중요하게 보는 제약

## 구현 요청 흐름

1. 사용자가 Navigator에 `8520`을 보낸다.
2. Navigator가 구현 요청이 충분히 구체적인지 확인한다.
3. 충분하지 않으면 사용자와 범위, 완료 기준, 검증 방법을 먼저 정리한다.
4. 충분하면 Forge에 구현 요청을 보낸다.
5. Forge는 구현, 테스트, 검증을 수행한다.
6. Forge는 최종 보고를 남기고 대기한다.
7. 사용자가 Forge에 `7410`을 보내면 Forge는 최근 구현 내역을 Navigator에 직접 전달하거나, 실패 시 현재 채팅방에 Navigator 전달용 보고서로 정리한다.
8. Navigator는 Forge 보고서를 확인한 뒤 사용자에게 변경 사항, 검증 결과, 남은 이슈를 정리해 보고한다.

구현 요청에는 다음 항목을 포함한다.

- 구현 목표
- 수정 대상
- 포함 범위와 제외 범위
- 완료 기준
- 검증 방법
- 관련 문서 경로
- 미정이지만 임시로 고정한 가정

## 문서화 원칙

- 중요한 결정은 채팅에만 남기지 않고 프로젝트 문서에 반영한다.
- 스펙이 바뀌면 관련 문서의 기준과 경계를 함께 갱신한다.
- 구현 중 바뀐 전제는 나중에 찾을 수 있도록 문서에 남긴다.
- 확정된 구현 방향과 임시 가정은 구분해서 기록한다.
- 팀원 스펙과 충돌하는 내용은 임의로 덮어쓰지 않고 충돌 지점으로 표시한다.

## 구현 전 확정 원칙

- 구현 방향이 확정되기 전에는 구현하지 않는다.
- 특히 `GOPS Forge`는 Navigator가 정리한 구현 요청 없이는 파일을 수정하지 않는다.
- MVP 범위, 제외 범위, 검증 방법이 불명확하면 구현보다 질문을 우선한다.
- 빠른 구현보다 잘못된 전제의 조기 발견을 우선한다.

## 구조 조정 원칙

이 협업 구조는 프로젝트 상태에 따라 조정할 수 있다.

- 팀원 스펙이 늘어나면 Compass의 검토 기준 문서를 확장한다.
- 구현 범위가 커지면 Forge에서 임시 서브에이전트를 사용해 탐색, 테스트, UI 검증을 나눌 수 있다.
- 현재는 별도 worktree를 사용하지 않는다.
- 프로젝트가 Git 저장소로 전환되더라도 worktree 도입은 별도 결정으로 다루며, 기본값은 같은 local 프로젝트 폴더 운영이다.
- 트리거 숫자나 채팅방 이름은 필요하면 바꿀 수 있지만, 변경 시 이 문서를 함께 갱신한다.
